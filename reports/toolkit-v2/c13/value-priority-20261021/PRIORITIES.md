# C13 priorities: comparative value and correct selection

AEEP should determine which capabilities help an already capable agent on a
particular task, then select and manage only applicable approved capabilities.
Infrastructure qualification establishes whether that process runs acceptably.
It does not establish capability usefulness or the value of AEEP's decisions.
This record implements the [operator's correction](operator-steering.json).

## Keep four kinds of evidence separate

| Claim | Required evidence | Current limit |
|---|---|---|
| Candidate adds task-specific value | Same capable baseline versus baseline plus optional candidate; matched tasks/settings, protected independent grading and frozen utility/guardrails | The completed mechanical-edit comparison is INCONCLUSIVE; no demonstrated marginal benefit |
| AEEP selects appropriately | AEEP policy versus credible static/discovery policies with the same available capabilities and authority; held-out decision records, verified task outcomes, abstentions and decision overhead | The completed campaign disabled admission by design, so it did not establish live selection quality |
| Management remains safe | Applicability at dispatch, current source/model/backend binding, revocation, preserved attempts and recovery | Existing synthetic contract checks test mechanisms; live applicability and adoption claims retain their own gates |
| Infrastructure operates acceptably | Baseline/incremental measurements on declared representative workloads and workload-justified operational targets | CLI calibration is limited; the proposed 1/2-second and 256 MiB figures are not accepted product requirements |

A genuine negative or inconclusive result is useful evidence for abstaining.
Always selecting nothing would also fail to demonstrate useful selection where a
capability has independently established applicable value. Qualification, loading
instructions and passing an infrastructure check cannot justify automatic use.

## What the existing evidence permits

[The retained decision audit](historical-decision-audit.json) verifies all four
arms passed 105/105 holdouts, zero success gain, unsupported material wall-time
benefit, missing trusted token pairs and unknown optional candidate use. Keep the
baseline and candidate unadmitted for this report. Do not turn that into a claim
that the candidate is never useful.

The campaign explicitly disabled admission. Its `admission=false` therefore
cannot prove AEEP's live selector independently made the right decision. This is
an evaluation gap, not a newly discovered runtime bug. The audit does not inspect
or mutate current routes. Existing [admission/applicability tests](../../../../tests/test_v08_assessment.py)
and [utility/dominance tests](../../../../tests/test_v08_incremental.py) cover
synthetic positive evidence, stronger challengers, missing metrics, scope drift,
revocation and authority limits. Their delayed baseline/constructed timings are
software fixtures, never real comparative usefulness evidence.

## Next work, in order

1. Choose representative work because the operator needs it. For the current
   coding-capability scope, use bounded repository maintenance: diagnosing and
   repairing a real regression, propagating a contract change across callers,
   and small/adjacent tasks where native tools may be sufficient. Prior observed
   collector-launch, callback-binding and report-provenance incidents are useful
   development/training examples, not new independent holdouts. Source and pin
   independent cases, rights, snapshots and hidden checks before a live study;
   do not choose tasks because a candidate already won on them.
2. Prepare the task/grader mapping using existing recipe extensions, workers,
   protected validation and report contracts. The current mechanical-edit grader
   does not establish arbitrary repository patch correctness. New real-task
   snapshots, patch validation and applicable worker conformance remain needed.
   Keep answers, future cases and grading assets outside trial workers.
3. Freeze the candidate-value comparison before holdout: actual task mix, capable
   baseline, optional candidate, ordinary competing tools, identical model/effort,
   order, verifiers, utility dimensions and existing evidence thresholds. Keep
   success/quality first; measure paired task time/tokens/cost only with their
   proper provenance. Negative and inconclusive outcomes remain valid.
4. Evaluate selection separately. Give static/discovery and AEEP policies the
   same capability inventory and supporting environment. Freeze eligibility and
   decision policy before independent tasks; record selected capability or
   abstention, evidence used, false admission, wrong-scope use, missed applicable
   value, verified outcomes and decision overhead. Compare with feasible stronger
   baselines; do not grant AEEP exclusive tools or select only invoked cases.
5. Observe infrastructure during those relevant authorized workloads. Add a
   diagnostic only when a specific measurement gap blocks interpretation or safe
   execution. A separate 30-command or 12-turn resource campaign is no longer the
   default next step. Do not replay the completed 564-task study.

This is a corrected work plan, not an executable study or new model/install
permission. No independent real-task holdout, new patch grader or selection-value
result is claimed. Reuse the existing stack; no new core service is proposed.

## Operational targets need workload evidence

The earlier 50-operations/day assumption, 200-record report profile, 1/2-second
p95, 256 MiB CLI RSS and 4 GiB incremental host target are unvalidated operational
hypotheses. Before adopting an SLO, record the actual task/input sizes, dependency
closure, frequency/concurrency, host load, observed distribution, user tolerance
and the consequence of exceeding it. Different useful workloads may warrant
other budgets. Do not project savings from invented daily volume or reuse a
calibration sample as held-out acceptance.

Existing security/input guards, permission ceilings, $0 cash authority, 50 GiB
host reserve and limits in actual exact execution reviews remain binding. Frozen
studies and their utility thresholds stay unchanged. Comparative resource benefit
and guardrails remain part of task value when predeclared; a workload-specific
absolute infrastructure target is a separate question. Account for AEEP decision,
setup and assessment overhead without presenting it as user-task savings.
