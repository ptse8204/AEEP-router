checks. Contributors and agents must follow it. Include it in delegated work
and preserve its authority and evidence rules.

## Experiment definition

Use the existing AssessmentService and BenchmarkRunner. Select direct execution,
controlled-agent comparison, or complete-workflow comparison in the reviewed
plan. Never switch structures or adapters after a failure. The initial
Spreadsheets experiment is a complete-workflow comparison: capable Codex with
files, shell, Python, pandas and openpyxl versus that shared environment plus
the entire selected plugin with its reviewed dependencies. A skill-only study
must give both arms identical supporting tools and libraries.

Freeze candidate, baseline, reference, adapter/version, dependencies, model and
reasoning settings, permissions, fixtures, grader, feature extractor, seed,
primary metric and worker condition. Both agent arms use the same adapter.
Changed definitions require a new plan and fresh holdout. Trial workers receive
only frozen task instructions, never this repository's contributor instructions.

Use eight screening, 28 training and 105 held-out cases. Distribute variations
with counts differing by at most one. Qualification requires at least 100
distinct holdouts, every admitted variation and no correctness failures.
Savings require 20 distinct fully measured pairs per resource. Repetitions do
not increase independent correctness counts. Historical comparisons retain their
wall-time policy. New incremental comparisons predeclare utility dimensions: a
confidence-supported 10% resource benefit or five-percentage-point task-success
improvement, with at most 10% regression on other declared guardrails. Correct
for multiple comparisons; group uncertainty by template and case; never pool
worker conditions. Feasible stronger baselines must not dominate an admission.

## Completion and rollback

Report implementation/compatibility, environment conformance, live acceptance,
controlled-fixture admission/revocation, savings and production support
separately. CSV, text, search and the reviewed workbook recipe each require live
qualification, marginal-value and native-catalog evidence. Negative plugin
results are valid. A labelled controlled fixture must exercise admission, use, revocation and stale-decision rejection regardless of
real candidates' outcomes. Never force a real plugin to win.

Historical router success, mocked hosts, skipped tests, manual flags and
experimental App Server success cannot establish production readiness. Keep
unfinished gates visible in reports/v08/plan-coverage.md. Budget exhaustion is
insufficient evidence, not permission to lower thresholds or silently increase
limits. A concrete operator-approved budget amendment is required for expansion.

Rollback revokes scoped automatic use, retains historical evidence and uses only
feasible configured baselines. Binary downgrade requires restoring a database
backup made with the earlier version; changing the schema version is unsafe.

## Reviewed executable recipes

For a new family that needs code, use a version-2 recipe with an
`ExecutableRecipeExtension`. Generator, grader and independent reference are
reviewed argv-only commands with bounded JSON input/output. They run in the
selected offline container through the existing controlled executor. Generated
code is never imported into the coordinator. The stored runtime definition also
binds AEEP source files before materialization; a changed runtime requires a new
request and review before any generator execution. Structural feature rules use
JSON Pointers and bounded length, type or enumerated-value inspection.

The operator first stores the recipe and prepares a materialization request with
`aeep assess prepare-recipe`. Review the recipe and environment digests, and bind
them to an existing grant or an operator-approved amendment. Then
`aeep assess generate-cases REQUEST_ID` spends that same grant to generate eight
screening, 28 training and 105 holdout cases. The generator must return distinct
inputs, explicit reviewed variations and template families, and balanced holdout
coverage. A failed or interrupted generation is not replayed automatically.

Use `aeep assess propose --case-set REQUEST_ID` to create the normal reviewed
assessment plan. A case set belongs to one plan; changed plans require fresh
cases. Before candidate execution, the campaign runs the contained independent
reference against every generated truth and the separately reviewed literal and
transformed fixtures. It challenges the grader with correct and faulty results.
A generator, reference or grader fault blocks assessment without counting as a
candidate correctness failure. Candidate and baseline results then use the same
BenchmarkRunner and acceptance thresholds as shipped recipes.

Generation, reference checks and grader calls have separate ledger operations.
Grading time is excluded from paired implementation wall time and charged as
assessment overhead. Container-client CPU and memory remain distinct from
unknown candidate resource measurements. Tests that replace containment with a
local subprocess are lifecycle fixtures only; the opt-in real-container test
runs the same recipe through actual Docker processes.

suggests deadlines without changing a grant. Review a fresh main plan and an

use a separately materialized case set; the pilot selects its eight screening

Link the completed pilot when proposing the main campaign with `--pilot-report
REPORT`. New proposals create a v6 main plan with explicit pilot lineage and the full
141 cases. Pilot trials are assessment overhead in the main report; their ledger
operations are included once and never debited again. Qualification, marginal
studies and worker-boundary probes likewise contribute their recorded costs.
Incomplete cost lineage keeps total cost and break-even unknown. The existing

V6 permits a primary-arm deadline change only to the pilot's calculated bound.
The frozen implementations, model settings, instructions, worker images and
permissions must otherwise match. Additional reviewed challenger dependencies
may be added, but existing executable dependencies cannot change. Renewed
conformance references are allowed because each new task profile must independently
pass the ordinary boundary and identity checks before invocation. Pilot evidence

## Protected worker sign-in

After the exact worker/bootstrap scope is approved, run `aeep assess
--manifest MANIFEST signin-worker REQUEST` in your own terminal. Codex presents
the device-login prompt directly there. Do not invoke this command through an
agent output-capture tool or paste login codes into chat. AEEP never pipes or
reads authentication output and never accesses the desktop credential cache.

Each sign-in reserves one setup operation and 330 seconds from the existing
grant: up to 300 seconds for login and bounded cleanup. It reserves no model
turns and no cash. Revocation stops new work; failed or interrupted sign-in keeps
its measured charge and cannot replay the same operation. Two sign-ins plus two
60-second connectivity probes reserve at most four operations, two model turns
and 790 seconds. A successful login process is not environment conformance.
The ordinary boundary checks still apply before candidate assessment.

## Turn-free post-login inspection

`aeep assess prepare-worker-inspection SOURCE_REQUEST` prepares a v2 conformance
request against the existing worker binding. Review its exact mapping and runtime
before `aeep assess inspect-worker REQUEST`. Each request is one-shot and reserves
one operation and 120 seconds from the same grant: up to 90 seconds inspection,
five seconds transport shutdown and 20 seconds worker removal. It reserves no
model turns and cannot authorize sign-in, candidate execution or admission.

The Codex adapter reads supported identity/model metadata, selected effective
configuration and managed requirements, then runs a fixed synthetic command via
`command/exec` without overriding the configured permission profile. Configuration
values are compared against reviewed expectations; raw configuration and unknown
values are not persisted. Inventory may initialize MCP processes, so inspection
skips it unless empty MCP configuration and disabled apps are observed explicitly.
Connection refusal or timeout is recorded as unreachable, not permission denial.

The record keeps partial observations, canonical events, elapsed cost and confirmed
cleanup. Successful inspection is not full conformance. Missing policy fields,
unavailable inventory, credential-canary checks, cross-worker checks and candidate
absence still need their own evidence. No model trial can use an inspection record
as a replacement for the existing boundary verifier.

The inspection command handles socket-creation denial as well as connection
denial. It records a hidden configuration path as `absent`, a read-only mount as
`read_only`, and other unavailable observations separately. None of these facts
alone establishes full conformance. The optional real Codex regression reads
`AEEP_INSPECTION_FIXTURE_SPECS`, a JSON list of one or two pinned executor specs.
It refuses credential volumes and all network bindings, calls only sandboxed
`command/exec`, and checks cleanup. It is an offline boundary test, not an
authenticated conformance run.

## Paired post-login probe review

`aeep assess prepare-pair-inspection` creates inert v3 conformance requests for
the existing protected worker pair. `inspect-pair` requires exact operator review
and reserves two operations on the same grant before launching either worker.
The first profile checks Spreadsheets and its actual shared/dependent libraries;
plugin metadata cannot supply arbitrary probe commands. It starts no model turns.

The runner keeps both private workspaces available for synthetic cross-worker and
external-answer checks. It creates a random synthetic credential canary using an
exclusive write, reads only that canary through the sandbox, and removes only the
exact created name. It never enumerates or reads authentication files. Fixed
policy, library, network, resource and interrupted-command probes produce separate
reviewed `BoundaryProbe` records linked to durable execution events and charged
operations. Malformed observations, drift, revocation or uncertain cleanup cannot
produce a passing pair. Partial evidence and reservations survive interruption;
request IDs are never silently replayed.

The bound is 240 elapsed seconds per operation (480 reserved seconds combined),
zero model turns and zero cash. Accounting sums the two measured worker-operation
lifetimes, including their paired synchronization; it is not a measurement of
candidate task performance. Passing these command probes does not establish model
stream completeness, a reviewed enforcement definition, full conformance or an
admission. Separately reviewed connectivity calls supply their own evidence.

## Scoped campaign copies

Campaign and recipe-operation copies must retain the current scope's definitions
and their dependencies, along with every admitted route's runtime dependencies
and task authority. Revoked admissions, reviews and grants remain revoked in the
copy. Missing required references or cyclic dependencies stop copying rather than
produce incomplete authority. A review alone does not make an unrelated historical
campaign a dependency of the current run.

This filtering applies to new scoped copies. It does not delete records from the
canonical store or discard existing attempts, accounting or recovery evidence.
Unscoped copying retains its prior behavior. Measure the actual materialized plan
and its finite operation count before approving an assessment's storage allowance;
a small preparation snapshot does not establish the size of every later copy.

## Durable bootstrap event streams

Connectivity bootstrap uses the same per-event persistence sink as controlled
Router invocations. New execution events use v2 and include their journal ID,
so nested journals sharing an attempt cannot collide under content-addressed
storage. V1 events retain their original serialized bytes. The evidence validator
rejects a v2 event attached to another journal. Partial events survive raised
errors and cancellation; missing final usage remains unknown and an uncertain
request cannot be replayed. A completed historical stream snapshot does not
prove pre-completion persistence in the earlier implementation.

## Exact task-profile inspection

Version-2 paired inspection accepts the reviewed workbook task configurations,
including artifact delivery and the treatment skill's exposure mode. It applies
the same native thread configuration and inventory checks as execution, then runs
only fixed synthetic boundary commands. It never calls `turn/start`, transfers a
task workbook or executes task instructions. Shared executor settings must match;
the candidate skill is the reviewed difference. V1 retains bootstrap-only scope.
Managed conformance checks require the probe's observed host identity, preventing
a task profile from borrowing a different profile's successful observations.


## Content-free grader diagnostics

Executable extension v3 adds an exact reviewed list of `failure_codes`. Its grader
returns parallel `valid` and `failure_codes` arrays: a successful check has null,
and a failed check has one declared code. Unknown codes, free text, extra fields
or inconsistent decisions block the campaign as a grader error. V1/v2 retain
their boolean-only contract and omit the new definition field.

Materialized case validators bind the reviewed codes into the immutable plan.
Trial validation retains a failed check's exact declared code in `detail`; all
other detail text is removed. Codes identify a condition, never cell values,
paths or task content. The workbook definition uses this contract for output,
sheet, extent, header, value, formula, cache, summary and preserved-sheet failures.
Its boolean acceptance rules are unchanged. Existing reviewed definitions and
historical outcomes are not rewritten; a new definition needs fresh review and
cases before execution.


V3 literal fixtures may also bind `grader_output`, a separately reviewed correct
artifact alongside the existing input and expected truth. Independent validation
checks these outputs before candidate trials and charges the ordinary grader
operations; previews include their upper bound. Earlier versions reject this
field, and absent values are omitted from historical serialization. Workbook
fixtures include equivalent inline and `str` text encodings. The grader preserves
text types and rejects unreviewed cell types; formulas, cached values, formatting
and structural requirements remain unchanged.


## Configured setup tools

`setup-options` / `aeep_assessment_options` list paginated operator-selected scope
and configured route identifiers. `setup` / `aeep_assessment_setup` use those
records and the existing grant to prepare a plan or contained fixture request.
Agent comparisons require capable workers and a reviewed experiment; the legacy
read-only initializer cannot satisfy this path. Definitions remain inert until
operator review. Model calls cannot define experiments, review code or amend
authority. The selected structure is saved in an inert setup record and carried
into the proposal. Existing plan choices remain the default for the same scope.

`aeep_assessment_generate_cases` executes only an existing reviewed request
through the contained recipe pipeline. It returns identifiers and counts, never
expected answers or fixture payloads. A repeated completed request returns the
existing case set without a second debit; interrupted operations remain unreplayed.
Setup proposals defer their measured preparation cost to the normal campaign
ledger; generation is charged immediately. Test scope rejection, revoked grants,
unchanged counters, missing worker bindings, choice persistence and answer exclusion.

New plans freeze all saved non-proposal setup costs for their exact subject,
including repeated static inspections and worker preparation. Later stages reuse
the same operation IDs, so shared setup is charged once. Earlier proposals follow
their explicit parent-plan/report lineage. Costs recorded after a plan is frozen
cannot silently change it. Historical plans and reports retain their original
cost references. A failed preparation with missing measurements remains incomplete;
do not create a measured setup record by replacing unknown values with zero.

## Catalog metrics relay

Opt-in App Server catalog collection uses the existing immutable worker and stdio
transport. The worker must bind the exact packaged collector source in its
reviewed files. Metadata snapshots keep hashed skill identities and bounded
numeric observations only; every snapshot has an opaque worker scope. Canonical
message events bind snapshot digests before final receipts. No snapshot claims
complete export or turns missing data into a negative discovery observation.

Test the real local HTTP/stdin/stdout path as well as normalization: wrong scopes,
malformed exports, duplicate keys, nonfinite/oversized values, snapshot rollback,
forged child frames, process interruption and cleanup. Native Codex probes use
network-disabled disposable workers and synthetic responses; they prove protocol
behavior only. Authenticated collector access restrictions and effective telemetry
policy require a newly reviewed worker profile. Enabling metrics must not expand
remote destinations, expose credentials or reset the assessment grant.

The complete real-boundary release check also requires a pinned
`AEEP_CATALOG_METRICS_IMAGE` containing the current collector, and
`AEEP_INSPECTION_FIXTURE_SPECS` containing credential-free, network-disabled
worker definitions. The native collector tests run with a synthetic local model
response server and verify the actual sandbox's collector denial. Their positive
injection observations are protocol evidence, never learned plugin selection.

## App Server final results

Treat explicit `commentary` messages as progress, never structured task output.
Use explicit `final_answer` messages when present; retain the legacy unphased
reply path for older hosts. Unknown phases fail protocol validation. Message
contents remain transient, and a commentary-only completion supplies no answer.
Actual stdio fixtures exercise progress followed by a structured final result.

### Scoped dynamic-tool composition

The operator-composed App Server bridge separates immutable behavior from execution
permission. The reviewed behavior binds declarations, executor fingerprints,
native backend, artifact semantics and finite permission/resource limits. Each
callback also binds its current reviewed task scope, canonical trial reservation
and outer attempt. Fresh case scopes may share a behavior definition only when
they match its complete executor mapping and remain within its limits. Their
attempt allowances remain separate durable records; database copies cannot reset
allowances. Changed programs, backends or permissions require new review and
applicable evidence. A declaration acknowledgement alone does not establish model
visibility, composite boundary conformance or campaign qualification.

### Human comprehension check

Prepare this check from an actual task result and its recorded receipt, then ask
a human participant to use the ordinary result and available inspection/control
interfaces. Do not supply the answers first. Record whether they can identify:

1. What changed, and what remained outside the task's scope.
2. What was checked, and any verification limits or unknowns.
3. What access or spending was authorized, and any approval still needed.
4. How to pause AEEP and undo its owned configuration changes.
5. What to do when the displayed outcome needs recovery or another approval.

Keep receipt identifiers, the exact presented summary, responses, help required
and observed errors together in the existing delivery record. Score each item
against the receipt and supported controls. An omitted or misleading field is a
product finding; do not coach the participant and count that response as unaided.
Record any repeat after a correction separately. These five questions and the
unaided/helped/incorrect/unanswered categories are fixed before the exercise under
the standing test-definition delegation. This small check measures comprehension
for that participant and journey; it does not establish population-wide usability.
Until an actual participant responds, report the human gate as not yet measured.
Agent reviews and automated wording checks cannot supply those responses.
